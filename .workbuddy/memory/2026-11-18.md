# 2026-11-18

## 本地化资源格式决策：保持 C# 字典现状
- 评估了 `PlatformBuiltInResources.cs`（C# 字典，en-US/zh-CN 各 822 条）是否改用嵌入式 JSON 或 `.resx`。
- **决定：保持现状字典，不改动**。
- 理由：
  - `.resx` 硬冲突——靠 satellite assembly，语言编译期固定，无法支持本项目"运行时通过 Localization 模块动态新增语言"（见 `PlatformRequestLocalization.cs` 注释、`GetSupportedLanguagesAsync`）及后台编辑词条（词条存 `ILocalizationStore`，`PlatformLocalizationService._storeSnapshot` 读取）。强类型优势在本项目无收益（全用字符串索引器 `L["..."]`）。
  - 嵌入式 JSON 虽能统一平台/模块加载路径，但收益不足以抵消搬运 822×2 条的风险，且当前功能正常。
- 项目现状：全仓 **0 个 .resx、0 处 IStringLocalizer**，本地化是完全自定义体系（自定义 `ILocalizationService` + HTTP 词典 + 模块运行时合并），不走 `IStringLocalizer`/resx。
- 若将来要改，仍推荐嵌入式 JSON（非外部文件、非 resx），签名 `Register(registry)` 保持不变。

## 多语言体系审查（面向未来「多语言管理模块」）
核心判断：整套设计是「读优化」，几乎没为「写/管理」留位置。分五层问题：
1. 资源来源：`PlatformBuiltInResources.Register` 只进 registry、不进 Store（管理模块要管理内置 822 条需先种子入库）；模块 JSON 在加载时读一次（`ModuleLifecycleManager:491-546`），管理模块改词后模块升级会被 JSON 覆盖回去。
2. 注册中心：`InMemoryLocalizationRegistry.BuildMerged:93-105` 按 ConcurrentDictionary.Values 遍历，同 key 跨模块覆盖顺序不确定；`Changed` 事件无任何订阅者；`GetAllEntries` 扁平化，丢失来源/可编辑标记。
3. 服务端：`PlatformLocalizationService._storeSnapshot:21-22` 只写不清，改 DB 后同步索引器读旧快照；回退链与前端各写一遍易漂移。
4. API：`LocalizationController` 全 `[AllowAnonymous]` + 只有 GET + 无 ETag/版本号/Cache-Control，无法支撑写操作与缓存失效通知；管理 API 需单独带权限端点。
5. 前端缓存（最大障碍）：`FrontendLocalizationService._cache` 是 static 进程级，`HasCulture` 命中永不重拉（中间件 `FrontendLocalizationExtensions.cs:49`）；`LoadAsync:87-89,116` 只接受「词条变多」快照——管理模块改值/删词（数量不变）前端永远看不到，除非重启 WebHost。
跨链路：`ILocalizationStore`（`LocalizationContracts.cs:70-76`）目前 0 实现，且接口只有读+SyncModuleResourcesAsync，缺 Upsert/Delete 词条、Add/Update/Delete 语言；`LanguageInfo` 缺 Id/IsBuiltIn/LastModified。
建议埋点（低改动）：给 resources API 加版本号/ETag，前端缓存按版本失效；registry 定义覆盖优先级；Store 接口预留写方法。

## 已落地：词条变更后的页面就地刷新地基（为 Localization 管理模块铺路）
用户确认"做在模块里"：管理模块负责 UI/写库/Store 实现，底层只留最小钩子。本轮已实现 4 文件：
1. `LocalizationContracts.cs`：`ILocalizationService` 新增 `InvalidateAsync(culture?, ct)` —— WebHost 前端与管理模块共用的失效入口（ALC 安全：用 Application 契约而非具体类）。
2. `FrontendLocalizationService.cs`：改显式构造函数注入（原 primary ctor），实现 `IDisposable`；新增进程级 `static int _version` + `static event GlobalChanged` + 实例 `Version` 属性；`InvalidateAsync` 清缓存（culture 空则全清）、`Interlocked.Increment(ref _version)`、`GlobalChanged?.Invoke()`。每个 scoped 实例构造时订阅 GlobalChanged→转发自身 Changed，Dispose 时精确退订（避免 static 事件持有 circuit 引用泄漏）。
3. `PlatformLocalizationService.cs`：补 `InvalidateAsync` no-op + 清本 scoped `_storeSnapshot`（registry 内置资源不变，无需处理）。
4. 两个 Layout（MainLayout + IdentityLayout）：`@key` 从 `FrontendLoc.CurrentCulture` 改为 `FrontendLoc.CurrentCulture + ':' + FrontendLoc.Version.ToString()`。
关键坑：Razor `@key` 指令不接受 `$"..."` 插值字面量（CS1056 意外字符 $），必须用 C# 字符串拼接表达式。
效果：管理模块保存词条后调 `ILocalizationService.InvalidateAsync()` → 所有在线线路就地重建页面子树、L[key] 取新值，SignalR 不断、无整页刷新。单进程够用；多实例副本时把 GlobalChanged 换成 Redis pub/sub 即可，接口不变。
现状：多语言三份缓存全是进程内内存（无 Redis），ILocalizationStore 仍 0 实现（由未来管理模块提供）。项目有 HybridCacheService（L1 内存+L2 Redis）但多语言未使用。
验证：dotnet build slnx 0 错 0 警；dotnet test 53/53。
注意：构建需先停用户 5100/5200 进程（dll 锁）；用户偏好 AI 直接改代码。

## 已落地：首次打开按浏览器语言设置默认语言（用户诉求）
截到首次 /setup 页是英文但期望跟随浏览器环境。根因两处：
1. WebHost 中间件 `FrontendLocalizationExtensions` 无 bb_culture cookie 时用服务端 `CultureInfo.CurrentUICulture.Name`（默认 zh-CN），完全不读浏览器 Accept-Language。ApiHost 的 `PlatformRequestLocalization` 虽支持 Accept-Language，但那是后端、不影响前端 SSR。
2. `UserPreferences.GetAsync` 首次无偏好时回落 `sysSettings.Public.DefaultCulture`(zh-CN)；且服务端 `UserPreferenceController.Get` 在用户从未保存时也返回默认 culture 的 DTO（非 null），fallback 根本用不上 → circuit 启动后 MainLayout 拿 zh-CN SetCultureAsync 覆盖首屏。
改动（3 处）：
- `FrontendLocalizationExtensions.cs`：加 `ResolveFromAcceptLanguage`（按 q 值降序，精确 culture 优先→两字母语言匹配，Supported 来自 `BuiltInLanguages` 的 zh-CN/en-US）；无 cookie 时解析并 `Response.Cookies.Append("bb_culture", ..., 365d, IsEssential)` 固化；解析失败回落默认。这样 SSR 首屏 + 后续线路都按浏览器语言预热/渲染。
- `UserPreferences.cs GetAsync`：`browserCulture = localization.CurrentCulture`（即中间件设的浏览器语言）；本机无 localStorage culture (`hasLocalCulture=false`) 且服务端返回默认 DTO 时，用 `value with { Culture = browserCulture }` 覆盖，避免 circuit 拉回默认；用户显式选过的语言（hasLocalCulture=true）不受影响。
- 支持语言目前只有 zh-CN/en-US：zh-*→zh-CN、en-*→en-US，其他语言回落 zh-CN（平台默认）。
闭环：首次无 cookie → Accept-Language 定语言 + 写 cookie → SSR 首屏与 circuit 一致 → 偏好层不覆盖；用户手动切语言写 localStorage+cookie，下次 cookie 优先。
验证：dotnet build slnx 0 错 0 警。需重启 5200 WebHost 并清掉旧 bb_culture cookie（或新开无痕窗口）才能看到首次行为。

## 已落地：多语言二次审查 BUG 修复（用户"全改"）
系统复审后修 6 处，改 4 文件：
1. 【失效变原始 key】`FrontendLocalizationService.InvalidateAsync` 原只清缓存就广播 → 布局 @key 变、子树重建时 L[key] 读空缓存整页变 key。改为先从 ApiHost 拉回最新词典覆盖缓存（失败则保留旧词）再递增版本广播。前提：ApiHost 侧管理模块须先失效其 store 快照。
2. 【预热倒退覆盖】`Prewarm` 原无条件覆盖 → 新标签页预热到旧词典会把线路已加载的更全词典倒退覆盖。改为与 LoadAsync 同构的 `dict.Count >= currentCount` 保护。
3. 【catch-up 不触发】预热命中缓存时 `EnsureLoadedAsync` 直接 return，LoadAsync 不跑 → 首次安装模块延迟注册的词条永久缺失。改为命中缓存也 `ScheduleCatchUpRefresh`；并用进程级 `static CatchUpScheduled` 按 culture 去重（每文化仅补刷一次）；补刷成功后改走 `_version++ + GlobalChanged` 全局广播（原来只 `Revision++/Changed` 仅本线路生效）。
4. 【跨设备偏好被覆盖】`UserPreferences.GetAsync` 原"本机无 culture 偏好就用浏览器语言"会覆盖跨设备保存的服务端偏好。改折中：仅当服务端返回的 culture 仍是默认值（从未显式保存）时才用浏览器 culture；服务端是非默认值则尊重它。
5. 【en-US 回退缓存空】`FrontendLocalizationExtensions` 预热主文化后，若非 en-US 也预热 en-US（回退链第二级），HasCulture 去重只多一次请求。抽出 `TryPrewarmAsync` 复用。
6. 【无效兜底语言】`AccountMenu.FallbackCultures` 去掉 ja-JP/de-DE（无词条会整页 key），只留 zh-CN/en-US，与 BuiltInLanguages 对齐。
验证：dotnet build slnx 0 错 0 警；dotnet test 53/53。需重启 5200 加载新 DLL。

## 已落地：模块词条覆盖顺序确定化（BuildMerged）
问题：`InMemoryLocalizationRegistry.BuildMerged` 遍历 `ConcurrentDictionary.Values`，同 key 跨模块的覆盖顺序由哈希桶决定、不确定。
关键事实：注册顺序本身已带正确优先级——平台资源在 `InfrastructureExtensions` DI 初始化时最先注册；模块由 `ModuleLifecycleManager.LoadAllAsync` 按 `ResolveLoadOrder()`（DisplayOrder + 依赖拓扑）串行 await 注册。故「后注册覆盖先注册」= 平台最低 < 先加载模块 < 后加载模块。
改动（仅 `InMemoryLocalizationRegistry.cs`）：
- 加 `static`→实例 `_registrationOrder`(ConcurrentDictionary<moduleId,long>) + `_nextRegistration`，`RegisterModuleResources(moduleId,...)` 首次注册时 `Interlocked.Increment` 分配序号（同模块多 culture 注册沿用同序号）。
- `UnregisterModule` 清序号（重装视为新注册、获更高优先级，序号表不无限增长）。
- `BuildMerged` 改为按 `_registrationOrder.OrderBy(Value)` 遍历（不再直接遍历 `_modules.Values`），序号大的后铺覆盖前者。
验证：dotnet build slnx 0 错 0 警；dotnet test 53/53。此改动在 ApiHost 侧，需重启 5100 加载新 DLL。
