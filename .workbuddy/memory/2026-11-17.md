## 纠正：项目登录鉴权已完成（上一轮回答错误）
用户质疑"登录鉴权都没做做了吧？"，实地核实后确认**用户是对的**，鉴权早已实现，且比预期完整。此前基于 README/旧记忆的判断错误，已在 MEMORY.md 更正。

核实到的实现（带位置）：
- `ApiHost/Auth/JwtTokenService.cs`：自签 JWT HS256 零外部包，签名密钥持久化 `data/auth.key`，access 默认 120s（可由系统设置覆盖）、refresh 7 天，两类 token 用 `typ` 区分防混用，校验用 `FixedTimeEquals`。
- `ApiHost/Auth/AppAuthentication.cs`：`AppBearerHandler` 校验 Bearer 并展开 claims（sub/name/email/sid/tid/roles/perms）；`HasPermission` 支持 `*` 通配与 `.write` → `.create/.update/.delete` 兼容；`RequirePermissionAttribute` 未登录 401 / 缺权限 403；`UseEndpointPermissionGuard` 统一守卫动态模块端点与 Minimal API。
- `ApiHost/Controllers/AppControllers.cs`：`IdentityController.SignIn/Refresh/RevokeRefreshToken`、`Register`/邮箱验证/重置密码（后三者挂 `auth-sensitive` 限流），其余 Controller `[Authorize]`。
- `ApiHost/Auth/CurrentUserFactory.cs`：从 DB 实时聚合角色、按钮权限码、菜单路径、租户；首个用户 + 系统"管理员"角色得 `*`。
- `WebHost/Auth/WebHostAuth.cs`：Cookie `bb_auth`（HttpOnly / SameSite=Lax / 7 天 / SlidingExpiration），`POST /auth/login` 写票据，`CookieAuthSession` 在 circuit 内无感刷新 access token，转 401/403 而非 302。
- `Web.Shared/Components/PermissionGate.razor` + `ICurrentUserPermissionService`：按钮/区域级权限门，支持 Codes 任一匹配与权限变更事件。
- `Modules.Identity.Frontend/Pages/SignIn.razor`：登录页（移植 Bluebird），`[AllowAnonymous]`。

仍存在的真实缺口（后续可修）：
1. 第三方登录 4 个按钮（Google/Microsoft/GitHub/Apple）均为 `NotifyUnavailable()` 占位。
2. `SignIn` 未挂 `[EnableRateLimiting("auth-sensitive")]`，而 Register/发码/重置有 → 登录接口缺暴力破解限流。
3. refresh_token 故意不轮换（Blazor Server circuit 无法回写浏览器 Cookie），7 天内稳定，仅 SignOut/Revoke 吊销——取舍有文档注释说明。
4. `AppControllers.cs` 类注释称"默认全部 RequireAuthorization（在 Program.cs 配置）"，但 `Program.cs` 实际只 `UseEndpointPermissionGuard()` + `MapControllers()`，无全局 fallback policy；当前靠各 Controller 标 `[Authorize]`，注释与实现不符（潜在漏标风险）。

结论：我上一轮评价里"登录鉴权都没做"是错的；原评价的架构结论（ALC 卸载、契约单一身份、双 Host 代价、前端半动态）仍成立，但"先砍掉一半平台能力把认证补上"这条建议作废。

## 修正：跨 ALC 分发的判断（11:48，用户质疑后重新分析）
用户问"模仿 MassTransit 能否做跨 ALC 分发"——**用户直觉对，我之前把它列进"明确不做"是错的，需区分两条路**：
- 之前否的是**进程内 `UseCaseDispatcher` 路线**：`MakeGenericType(useCase.GetType())` 按 CLR 具体类型解析 handler，模块 ALC 里的 handler 类型身份与宿主不一致 → 确实跨不了 ALC。
- **MassTransit 式消息总线天然跨 ALC**（甚至跨进程）：消息是 envelope（契约名 + 序列化 body），consumer 按契约名注册/匹配，不依赖 CLR 类型身份。所以"跨 ALC 分发"在这条路上是卖点而非障碍。
- 真实陷阱：① 队列里绝不能持有模块 CLR 对象引用（会成为 GC root 阻止 collectible ALC 卸载），必须存序列化后的 byte[]/JSON；② 模块卸载/换版本后 consumer 消失，envelope 要带 version + 无消费者策略；③ outbox/幂等/重试/死信都要持久化，研究阶段明确不做，只做 in-process 无持久化。
- MassTransit 授权实况（2026-11 查证）：v8 及以前 Apache-2.0 真开源（支持到 2026 年底）；v9 起商业、source-available、license file 按产品/组织授权（非按消息量），年营收 <100 万美元可申请 100% 折扣但仍是商业授权。ADR 0005 里"需运行时 license key"的表述略过时（最初计划的运行时检查已取消），但"禁用 v9+"结论正确。模仿设计思想不侵权，照抄源码违反其 license（禁止 derivative works）。

- `docs/CACHING.md`（新增）+ README 索引一行。

**踩坑/决策**：
1. `ConcurrentDictionary.AddOrUpdate` 的 update factory 在写竞争下可能重入 → 引用计数摘锁不可靠 → 改 `GetOrAdd` 永久锁（key 来自有限业务集合）。

## 补上 Redis L2 缓存（12:25）
用户指出只有内存缓存不够，要求 Redis。已实现 `HybridCacheService`：L1 = `MemoryCacheService`，L2 = `RedisCacheStore`；未配置 Redis 时 L2 全部 no-op，行为等价于纯内存缓存。

关键实现点：
- `RedisCacheState` 静态状态 + 惰性连接：安装向导在应用启动后才写 Redis 连接串，因此 DI 构建时不能固定是否启用 L2。`SetupInitializer` 调 `RedisCacheState.Configure(configuration.Redis)`；`HostPlatformExtensions` 调 `AddBlazorBoilerplateCaching(configuration, contentRootPath)`，后者优先读 `Infrastructure:Redis`，回退读 `data/blazorboilerplate.settings.json` 的 `infrastructure.redis`。
- `StackExchange.Redis` 2.10.1（本地 NuGet 已缓存）；`RedisConnectionProvider` 懒建/按连接串变化重建 `ConnectionMultiplexer`，`AbortOnConnectFail=false`。
- Redis key：`bb:cache:v:{key}` 存 JSON envelope（Value/Tag/AbsoluteExpiresAtUtc/SlidingExpirationTicks），`bb:cache:t:{tag}` 是 SET 索引；滑动过期读取时 `KeyExpireAsync` 续期并受绝对过期上限约束。
- 跨节点 L1 失效：pub/sub channel `bb:cache:invalidate`，消息 `{nodeId,type,value}`，跳过发送方自身；`RedisCacheInvalidationSubscriber` 后台订阅，未配置时空转等待，配置后自动接入。
- Redis 异常一律 fail-open（记录日志），不让缓存故障拖垮 API；L1 仍可用。
- `MemoryCacheService` 新增 `TryGet`、`SetWithOptionsAsync`、`RemoveLocal`、`RemoveLocalByTag` 供 Hybrid/订阅器使用，原 ICacheService 行为不变。
- 测试：Hybrid 新增 5 例（L2 回填 L1、复用 L2 factory 不执行、双层写入、双层删除、tag 只失效匹配 key）；`dotnet test` 29/29 通过。
- 文档/页面：`docs/CACHING.md` 重写为 L1+L2 设计；README 索引、Setup 页 HelpText、docker-compose 注释同步。仍明确未做：L2 EF 查询缓存、Redis health probe、配置运行中清空后的连接销毁。
